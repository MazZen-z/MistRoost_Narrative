## 1. 目标

## 2. 现状

- 【现状】主角**没有背包组件**。背包是 [`UMistInventorySubsystem`](../../../../MistRoost/Source/MistRoost/Public/Item/Inventory/MistInventorySubsystem.h)（GameInstance 子系统）持有的一个 `UMistInventory`，容量取项目设置（默认 24 格，快捷栏取前 9 格），换关卡不丢。
- 【现状】[`UMistInventory`](../../../../MistRoost/Source/MistRoost/Public/Item/Inventory/MistInventory.h) 本来就是通用容器，注释写明"玩家背包、箱子、出货箱共用这一个类"；堆叠、"全放或全不放"、跨容器转移都已有。
- 【现状】物品表只有 `BaseSellPrice`（Normal 等级售价）和 `bSellable`，**没有买价**；等级售价倍率在 `DT_ItemTiers`。
- 【现状】钱包 `UMistWalletSubsystem`：`TrySpendGold`（钱不够不扣）、`AddGold`。出货箱：投入后次日结算。
- 【现状】背包、钱包都还没接存档（13 篇 §3 存档说明）。

## 3. 每个人的背包：流程（Q11）

### 3.1 一句话

**每个 NPC 都有一个自己单独的背包**——一个独立的 `UMistInventory` 容器，里面就是他可交易的东西。背包由背包子系统**保管**，按名字取；NPC 身上的背包组件是"钥匙"，本身不装东西。像银行保险箱：每人一个箱子、互不相干，钥匙在自己身上，箱子放在银行。

子系统不是"一个大家共用的大包"，而是"保管处"：里面是一排各自独立的包，每个包有主人的名字。

### 3.2 为什么箱子不直接放在 NPC 身上

NPC Actor 会被关卡卸载（走到别的地图、世界分区流送），Actor 一销毁，挂在它身上的东西就没了。要保住，只能在卸载前把背包拷出去、加载后拷回来——容易漏拷、重复拷，最后还是得有个地方存着，绕一圈又回到"子系统保管"。主角背包现在就是这么做的（放在子系统里，换关卡不丢）。

### 3.3 以木匠为例：一个背包的一生

| 步 | 什么时候 | 发生什么 |
|---|---|---|
| 1 配表 | 做内容时 | 身份表里木匠 `ShopId = Shop_Carpenter`；库存表列出他卖什么（木料 ×20、木板 ×10、春季才有的竹子……） |
| 2 建包 | 新游戏开始 | 子系统给每个配了商店的 NPC 建一个**独立**容器，名字＝`Npc.` 加 NpcId，即 `Npc.Carpenter`，按库存表装满。木匠还没见过面、他所在的关卡没加载，包也已经在了 |
| 3 拿钥匙 | 木匠出现在关卡里 | 他身上的背包组件按名字去子系统领到这个包 |
| 4 交易 | 玩家和他交易 | 界面左上显示这个包；买卖直接改这个包（§9） |
| 5 离开 | 玩家去别的地图 | 木匠 Actor 被卸载销毁；包还在子系统里，一个不少 |
| 6 回来 | 再次加载关卡 | 新生成的木匠又领到**同一个**包 |
| 7 每周一 | 星期一早上 | 清空（玩家卖给他的也一起清，Q12）→ 按库存表重新装 |
| 8 存档 | 存档／读档 | 子系统按名字存所有包；读档按名字还原 |

### 3.4 怎么保证可控

| 关心的事 | 做法 |
|---|---|
| 谁能改 NPC 的包 | 只有三处：成交事务（§9）、每周一补货、调试命令；界面和其他系统只读 |
| 随时看得到 | `Mist.Inv.Dump Npc.Carpenter`，木匠不在场也能看 |
| 配置出错 | 启动体检：库存表装不下、ItemId 不存在、价格为负、两个 NPC 指向同一家店 |
| 包会不会串 | 容器名＝`Npc.`＋NpcId，NpcId 在身份表里唯一，同一个名字永远是同一个包 |
| NPC 从表里删掉了 | 包保留不删（不丢玩家卖给他的东西），体检警告 |

### 3.5 背包组件的两种模式

| 模式 | 数据在哪 | 存档 | 用于 |
|---|---|---|---|
| **常驻** | 背包子系统，按名字 | 存 | 主角（`Player`）、NPC（`Npc.<NpcId>`）、以后的箱子（`Chest.<Id>`） |
| **临时** | 组件自己持有，随 Actor 消失 | 不存 | 以后"偷了东西、被打倒时吐出来"这类怪物 |

主角也挂一个常驻模式的组件，指向 `Player`——现在的背包行为完全不变，只是主角和 NPC 从此对称。

### 3.6 以后的怪物掉落（只描述流程，本轮不做）

怪物是一次性的：刷出来、被打倒、消失，**不需要常驻背包**。掉落是"倒下那一刻现掷"：

1. **配表**：`DT_LootTables`（掉落表），每行：物品、数量范围、概率、条件（如 `Season == Winter`）；怪物定义里指一张掉落表。
2. **被打倒**：按掉落表经运气系统掷骰（全游戏概率都走运气入口，[程序设计准则 §2](../../../../MistRoost/程序设计准则.md#architecture)），得到若干物品堆。
3. **落地**：在地上生成可拾取物；或直接进主角背包，放不下的掉在地上。
4. **带了东西的怪物**（偷来的）：它的背包组件用临时模式，倒下时把包里的东西一起掉出来。

NPC 背包、箱子、怪物掉落都用同一个 `UMistInventory` 容器类和同一张物品表，区别只在"数据放在哪、要不要存档"。

## 4. 商店

**`DT_ShopDefs`**（行名＝ShopId，如 `Shop_Carpenter`）：

| 字段 | 说明 |
|---|---|
| DisplayName | 店名，如"木作铺"（占位） |
| Capacity | NPC 背包格数【占位】24 |
| OpenCondition | 营业条件，条件语言，如 `Hour >= 9 & Hour < 17` |
| ClosedText | 打烊提示，弹窗里"交易"置灰时显示 |
| RestockDay | 每周哪天清空并重新上货，默认 `Mon`（Q12）；`Never`＝不自动补 |
| AcceptFilter | 收购范围：`AnySellable`（默认）／指定物品类型／指定物品 |
| BuyMarkup | 没写死价格时，买价＝基础售价 × 它【占位】2.0 |
| SellFactor | 收购价＝基础售价 × 它【占位】1.0 |

**`DT_ShopStock`**（一张表管所有商店）：

| 列 | 说明 |
|---|---|
| ShopId | 哪家店 |
| ItemId、Tier | 卖什么、什么等级 |
| Quantity | 每次上货装多少；要"管够"就填一堆的上限（如 99），不做"无限" |
| Price | 写了就按这个卖（这就是该等级的单价）；0＝按 `BuyMarkup` 算 |
| Condition | 上架条件，如 `Season == Spring`、`Hearts >= 4`；在上货那一刻求值 |
| SortOrder | 显示顺序 |

- **NPC 与商店的关联只写一处**：身份表的 `ShopId`（[16 篇](16-NPC对话.md) §3）。启动时 NPC 域把"这家店的店主是谁"告诉商店子系统（上层告诉下层，方向合规），条件里的 `Hearts` 就指店主。
- 每周一早上（时钟 `OnDayStarted`，且 `DayOfWeek == Mon`）：清空 → 按库存表重新上货。新游戏第一天也按库存表上一次货。

## 5. 定价

```text
买（玩家付钱）：库存行写死价 或 基础售价×BuyMarkup×等级倍率 → ×(1−最优折扣) → 波动【后续】→ 向上取整 → 护栏
卖（玩家收钱）：基础售价×SellFactor×等级倍率          → ×(1+最优加价) → 波动【后续】→ 向下取整 → 护栏
```

- 等级倍率就是 `DT_ItemTiers` 现有的售价倍率，不另存。
- 取整对玩家略不利（买向上、卖向下），防止 ±1 的套利。
- 每次报价生成一个 `FMistPriceQuote`：原价、现价、生效规则的显示名（如"熟客价 9 折"）。**界面只显示报价，不自己算。**

## 6. 好感打折

**`DT_PriceRules`**：

| 列 | 说明 |
|---|---|
| ShopId | 空＝所有商店 |
| Direction | `Buy`（玩家买，打折）／`Sell`（玩家卖，加价） |
| Match | `Any`／`ItemType:Material`／`Item:Wood` |
| Condition | 条件语言 |
| Percent | 幅度，如 −10（买便宜 10%）、+20（多收 20%） |
| Label | 显示名（FText），界面上的小标签 |

示例【占位】：

| ShopId | Direction | Match | Condition | Percent | Label |
|---|---|---|---|---|---|
| Shop_Carpenter | Buy | `ItemType:Material` | `Hearts >= 2` | −5 | 熟客价 |
| Shop_Carpenter | Buy | `ItemType:Material` | `Hearts >= 5` | −10 | 熟客价 |
| Shop_Carpenter | Buy | `Item:Wood` | `Hearts >= 8` | −20 | 知己价 |
| （空） | Buy | `Any` | `Festival == SpringFair` | −10 | 庙会特价 |

- 同一方向命中多条时**只取最优的一条**，不叠加：好预期，也不会叠爆。
- 这里的 `Hearts` 就是好感心数；交易（Economy 域）不需要认识好感域，条件函数在中间（[14 篇](14-条件与世界事实.md)）。
- 参考：沙石镇店主随关系等级给折扣，最高约 25%（出处见 [13 篇](13-NPC系统总览.md) §9）。

## 7. 反套利（必须成立）

**任何渠道的最低买价 > 任何渠道的最高卖价**（渠道＝所有商店＋出货箱），否则"低买高卖"能无限刷钱。

- **启动体检（按最坏情况）**：对每件同时"能买到"又"能卖掉"的物品，取所有商店的最低可能买价（最大折扣）与所有渠道的最高可能卖价（最大加价、出货箱价），前者必须更高；不满足的规则或库存行逐条列出。按占位数：最大折扣 20%、将来按喜好的最大加价 20% → 2.0 × 0.8 ＝ 1.6 倍 > 1.0 × 1.2 ＝ 1.2 倍，成立；折扣做到沙石镇的 25% 也成立（1.5 倍）。
- **运行时护栏**：同一时刻、同一家店、同一物品等级，成交买价至少比卖价高 1。
- 买回自己卖掉的东西（§10）按正常买价，由上面两条保证不亏钱刷钱。

## 9. 成交（每一笔都是一次同步完成的事务）

**买**：

1. 重新报价（不信界面缓存）。
2. 检查：NPC 这格数量够、钱够（`CanAfford`）、主角背包放得下（`CanAcceptAll`）。
3. 提交：扣钱 → NPC 容器扣物 → 主角容器加物（全放或全不放）。第 2 步已全部检查，理论上不会中途失败；万一失败，回滚已做的步骤。
4. 记账：买入统计；广播 `OnTradeCompleted`。

**卖**：

1. 重新报价；检查这家店收不收（`AcceptFilter`、物品 `bSellable`）。
2. 检查：主角这格数量够。
3. 提交：主角容器扣物 → 加钱 → 放进 NPC 容器；**放不下的部分算 NPC 自己用掉了**，不报错，成交照常。
4. 记账：卖出统计；发 `ItemSold` 消息（当事人＝这位店主，[14 篇](14-条件与世界事实.md) §5）——你要的"主角卖出什么之后 NPC 会说某些话"就从这条消息来；广播 `OnTradeCompleted`。

**失败提示**（界面提示＋店主气泡台词）：

| 情况 | 情境 |
|---|---|
| 钱不够 | `Trade.NoMoney` |
| 他不收这个 | `Trade.Refuse` |
| 主角背包满 | 界面提示"背包满了" |
| 这格卖完了 | 格子已空，不可选 |

确认后数量框立即关闭，按钮在提交期间不可再按；成交是同一帧内的同步调用，连点不会重复扣钱。

## 10. 卖出的东西去哪（Q12，已定）

进 NPC 背包（放得下的部分），玩家可以按**正常买价**买回来；每周一早上清空并重新上货。

## 11. 后续 Feature：按喜好调价（MR-TRADE-002，本轮不做）

- 定价管线里"价格规则"之后已经留了"波动"一级。
- 大部分可以直接用现有写法：`DT_PriceRules` 里写 `Sell`＋`ItemTaste == Love` → +20，`ItemTaste == Hate` → −30。`ItemTaste` 是店主对这件物品的礼物喜好，与送礼用同一套判定（[17 篇](17-好感度与送礼.md) §6）。
- 每日随机波动（"今天鱼价高"）：按天固定地掷，读档不变。
- 开工前要另写设计：玩家怎么知道价格变了（价签颜色？店主一句话？），以及与出货箱价格体系的关系。
