## 2. 条件在编辑器里长什么样

凡是要配条件的地方（台词行、库存行、价格规则、记忆规则……）都有一个**条件列表**：

- 列表里每一项，先从**下拉**里选条件类型（季节、心数、旗标、听说……），再填它自己的几个字段。
- 列表里的各项**全部成立**才算成立（**且**）。列表空＝恒真。
- 每一项都有一个"**取反**"勾选框（**非**）。
- 下拉里有两个"组"：**任一成立**（**或**）和**全部成立**（且，用来在"或"里面再套一层）。组里又是一个条件列表，可以一层套一层。

例：春天、心数 ≥ 3，并且（是春庙会，或者序章还没结束）：

```text
条件列表（全部成立）
├─ 季节 ＝ 春
├─ 心数 ≥ 3
└─ 任一成立（或）
   ├─ 节日 ＝ SpringFair
   └─ 旗标 MQ_PRO_010_Done 已设        ☑ 取反
```

**程序上**（示意，实现时以代码为准）：每种条件就是一个**单独的结构体**，继承同一个基类，自己实现"判断"：

```cpp
// World/Clock 域里：一种条件＝一个结构体
USTRUCT(meta = (DisplayName = "Season"))
struct FMistCondition_Season : public FMistConditionBase
{
    GENERATED_BODY()

    UPROPERTY(EditAnywhere, Category = "Condition")
    EMistSeason Season = EMistSeason::Spring;

    virtual bool Evaluate(const FMistConditionContext& Context) const override;   // 读时钟，比季节
};

// 用的地方（例如对话行）只放一个列表，编辑器自动给出下拉：
UPROPERTY(EditAnywhere, Category = "Condition")
TArray<TInstancedStruct<FMistConditionBase>> Conditions;
```

- **加一种新条件＝新建一个结构体、写好判断**；编辑器下拉里自动出现它，别处都不用改。
- 取反、且、或由基类和两个组结构体统一处理，具体条件不用管。
- 每种条件还实现"体检"（引用的 ID 在不在表里）和一句"描述"（调试时打印成人能读的话）。

## 4. 条件放在哪一层

条件基类、"任一成立""全部成立"两个组放在 `Core/Condition`（第 0 层），不认识任何玩法；**每种具体条件放在它数据所在的域**（季节在 `World/Clock`，心数在 `Narrative/Relationship`……），各自继承基类。依赖方向始终是上层认识下层，合规（[程序设计准则 §3](../../../../MistRoost/程序设计准则.md#domains)）。

## 5. 消息管道与 NPC 记忆（你的想法）

**流程**：

| 步 | 发生什么 | 例 |
|---|---|---|
| 1 发消息 | 玩法系统在状态改完之后，往消息管道发一条消息 | 卖给木匠 3 个萝卜 → `ItemSold`（物品 Radish、数量 3、当事人 木匠、渠道 Trade） |
| 2 谁听到 | 按记忆规则表：当事人立刻知道；其他人按"传开天数"之后知道 | 木匠当场知道；其他人第二天早上听说 |
| 3 记住 | 听到的 NPC 在**自己的记忆**里记一条，带过期时间；同一件事再发生就合并累加，并重新算作"还没提过" | 木匠记住"主角卖了萝卜 ×3，3 天后忘" |
| 4 改台词 | 台词行的条件选"听说：ItemSold，萝卜" | 木匠打招呼时可能说"听说你的萝卜卖出去了？" |
| 5 有概率 | 台词行的"概率"列（[16 篇](16-NPC对话.md) §4），如 40%；没抽中就照常说本来的话 | 大约六成的日子木匠照常寒暄 |
| 6 说过就算 | 这句说出来后，对应记忆标记"已提过"，同一件事不再说；再卖一次＝新消息，又可能说 | |
| 7 忘掉 | 过期的记忆每天早上清掉 | 3 天没提就忘了 |

- **"谁知道"和"谁会说"分开配**：规则表决定谁听得到；只有台词表里配了"听说"那句的 NPC 才会说。没配的 NPC 记住了也不会提。
- 没抽中概率的日子，记忆还在；只要没过期，之后几天仍可能提起——像真人一样"想起来才说"。
- 每个 NPC 最多记【占位】32 条，满了挤掉最旧的。
- 记忆按 NpcId 存在子系统里：NPC 不在场也照样"听到"，关卡卸载也不丢。
- 长期的"一共卖过多少"用"累计卖出"条件，适合"卖了 100 个萝卜以后叫你萝卜大王"这类。

**记忆规则表 `DT_NpcMemoryRules`**（行名＝规则 ID）：

| 列 | 说明 |
|---|---|
| EventId | 哪种消息，如 `ItemSold` |
| Filter | 条件列表（下拉），对消息里的物品／人判断；空＝都算。如只记作物：上下文物品类型＝作物 |
| Participant | 当事 NPC 是否立刻知道 |
| Others | 其他人：`All`（全村）／`None`／共享池名（如只有 `Merchant` 池的人关心） |
| SpreadDays | 其他人在事情发生后第几天早上听说【占位】1 |
| RememberDays | 记几天【占位】3 |

**v1 的消息**：

| 消息 | 谁发 | 参数 | 阶段 |
|---|---|---|---|
| `ItemSold` | 出货箱结算（没有当事人，渠道 ShippingBin，发生日＝投入那天）；交易成交（当事人＝店主，渠道 Trade） | 物品、数量、渠道 | B（出货箱已有）、E（交易） |
| `GiftGiven` | 送礼 | 物品、收礼人（当事人）、档位 | D【已做：`UMistGiftSubsystem` 发布，档位写在附加名里（Love／Like／Neutral／Hate），数量 1】 |
| `ItemHarvested` | 种田收获一格（2026-09-28，技艺 K1 加） | 物品（作物）、数量 | 已做；技艺听它给农事经验 |
| `ItemCrafted` | 制作做出东西（2026-09-27，[25 篇](25-制作.md)） | 物品（产物）、一共几件、附加名＝配方 | 已做；技艺听它给制作经验 |
| 【后续】 | 钓到鱼、节日结束、完成任务…… | | |

加一种消息＝发布方在代码里发它＋规则表加一行；NPC 记忆这边的代码不用动。

**B 实现（2026-09-25）**：`Narrative/Memory`：`UMistNpcMemorySubsystem`（只订阅规则里出现过的消息名；"今天"取自消息管道，到期的传开和遗忘在每次查询时顺手处理，不挂每天开始的事件）、`UMistNpcMemoryRegistry`（项目设置 MistRoost - Narrative 的 NpcMemoryRuleTable）、条件"听说"。`DT_NpcMemoryRules` 先放一行 `ItemSold_All`：当事人当场知道，其他人（全村）第二天早上听说，记 3 天。对话说出一行台词（或确认一个选项）时，它条件里以"成立"身份起作用的"听说"会把对应记忆标为已提过——条件内核为此加了 `MistCondition::ForEachLeaf`（逐个访问列表里的具体条件，钻进组、算上取反），内核本身仍不认识任何具体条件。"已结识""今天聊过"记在 `Narrative/Relationship` 的 `UMistRelationshipSubsystem`（好感、送礼随 C、D 加进去）。

## 6. 状态从哪来：谁的数据谁管

没有"万能事实库"。每个域管自己的数据、定义自己的条件；条件内核只负责且、或、非。这与存档的做法一致（各系统自己认领存档块，见 `MistSaveGame.h` 的说明）。

### 6.1 剧情旗标

- **先声明后使用**：`DT_StoryFlags`，行名＝旗标 ID（如 `MQ_PRO_010_Done`），列：说明、所属剧情、Owner、可否清除。条件里的旗标字段只能从这张表里选（下拉），不会写错字。
- 谁来设：对话效果"设旗标"（16 篇）、剧情系统【后续】、调试命令。
- 本组不做剧情节点、排队与互斥——那是剧情编写准则 §4 的合同，由剧情系统负责；这里只提供"剧情过后"能被条件读到的那一位。

### 6.2 卖出统计

- 记每件物品的累计卖出数、累计买入数（给"累计卖出"条件、以后的成就与图鉴）。
- 来源与消息相同：出货箱结算、交易成交。短期反应用消息与记忆（§5），长期累计用统计，两者不重复表达同一件事。

### 6.3 节日日历

- `DT_Festivals`：行名＝节日 ID；季节、起止日、显示名（FText）。
- 节日有哪些、玩什么不在本组范围，先放一行占位供台词测试。
- 表放在 World 域、与季节表同处；"节日是否固定天气"等设计由 [季节与天气](10-季节与天气.md) 后续补。

### 6.4 时钟派生

- 【现状】`FMistGameTime` 有年、季、日、时、分、绝对天，**没有星期**。
- 给时钟补 `DayOfWeek`（由绝对天推：第 1 年春 1 日＝星期一），每周送礼上限（17 篇）和每周一清空 NPC 背包（18 篇）都要用。

## 7. 程序怎么做

| 部件 | 说明 |
|---|---|
| `FMistConditionBase`（`Core/Condition`，第 0 层） | 所有条件的基类：`Evaluate(上下文)`、`Validate(体检)`、`Describe()`；带"取反"字段 |
| `FMistCondition_AnyOf`／`FMistCondition_AllOf` | 或、且两个组；取反由基类处理 |
| `MistCondition::EvaluateAll(列表, 上下文)` | 列表全部成立才为真；空为真。无副作用、可重复调用 |
| 具体条件（各域） | `FMistCondition_Season`、`FMistCondition_Hearts`、`FMistCondition_Heard`…… |
| 上下文 `FMistConditionContext` | 世界上下文对象、当前对象 NpcId、上下文物品（送礼／交易时）、主角 Pawn（可选） |
| `UMistEventBusSubsystem`（GameInstance，`Core/Event`，第 0 层） | 消息管道：发布方先声明消息名，之后 `Publish`；订阅方 `Subscribe`。同步派发，**只在状态改完之后发**（程序设计准则 §2）。【实现】声明改为发布方 .cpp 里的静态声明（`MistGameEvents::FDeclaration`），模块加载时就登记好，编辑器下拉和启动体检不依赖子系统初始化顺序；消息没填发生日时，由时钟接上的"今天"补 |
| `UMistNpcMemorySubsystem`（GameInstance，`Narrative/Memory`，第 4 层） | 订阅消息、按规则表分给各 NPC、管理"待传开""已提过"和过期；提供"听说"条件 |
| 消息结构 | 消息名、物品、数量、当事 NPC、附加名（渠道、任务 ID 等）、发生日。够筛选用，不做任意载荷 |

- 运行期取不到数据（例如子系统还没起来）按"不成立"处理并只警告一次，不崩。
- 条件字段里的 ID（物品、旗标、NPC、节日、消息）尽量做成下拉，只能从对应表里选。

- **在代码里造条件项用 `MistCondition::Make(条件)`**：直接写 `TInstancedStruct<FMistConditionBase>::Make(非 const 变量)` 会命中引擎"按参数就地构造"的那个重载，模板参数退回基类，派生部分被切掉——自动化测试里实际踩到过。编辑器里配的不受影响。
- 占位数据：`DT_Festivals` 一行 `SpringFair`（春 13 日），`DT_StoryFlags` 一行 `MQ_PRO_010_Done`。都只在建行时由 `MistRoost/Tools/data_tables_build.py` 写，之后以编辑器为准。
- 存档块（§10）【09-26 已接】见 [20 存档](20-存档.md)：旗标、买卖统计、NPC 记忆睡觉时存、开游戏读回。

**考虑过、没选的做法**：

| 做法 | 没选的原因 |
|---|---|
| 文字表达式（写在表格里，程序解析） | 你选了下拉；文字写法要记语法 |
| 一个结构体装"类型枚举＋一堆通用参数" | 条件少时省事；但各条件参数差别大（心数要 NPC＋数值，卖出要物品＋数量，节日要节日名……），面板上堆满用不到的字段；结构体不能包含自己，"或里套且"做不了 |
| 引擎自带的 WorldConditions 插件（SmartObjects 在用，下拉＋且／或＋取反都有） | 其实就是引擎版的"每种判断一个结构体"。5.8.2 源码里仍标 `IsExperimentalVersion: true`、版本 0.1；它是"带缓存的条件"，每判断一次要 Schema＋上下文数据＋QueryState 走激活 → 判断 → 停用，给"当场判断一下"用太重；几千行对白都存它的格式，引擎升级一旦改格式，迁移成本在我们这边。以后 NPC 日程用上 SmartObjects、想复用条件时，写一层薄转接即可 |
| 固定列（季节列、心数列、旗标列……） | 每加一种条件就改一次表结构和所有表 |
| 用现成的消息路由插件 | 引擎里没有通用消息路由（已查 5.8.2 引擎插件目录）；Lyra 的 GameplayMessageRouter 是示例工程里的插件，不随引擎发，引入要走 [程序设计准则 §9](../../../../MistRoost/程序设计准则.md#plugins) 的评审。我们只需要"声明、发布、订阅"三件事 |

**下拉的代价**：这些结构在 CSV 里没法手写，所以**配了条件的表都在 UE 编辑器里编辑**。对话的文字另放字符串表，仍可用表格批量写（[16 篇](16-NPC对话.md) §14）。

## 8. 启动体检与降级

表加载时对每个条件做体检，**一次列完所有问题**（沿用 `UMistDataRegistry` 的体检风格，日志形如 `DialogueTable Carpenter validated 132 rows, 2 issue(s)`）：

| 检查 | 例 |
|---|---|
| 条件类型没选（空的一项） | 列表里有一项忘了选类型 |
| 引用的 ID 不存在 | 删掉了的物品、没声明的旗标、不存在的 NPC、节日表里没有的节日、没声明的消息名 |
| 数值越界 | 时辰填了 25、日期填了 30 |
| 空的组 | "任一成立"里一项都没有 |

- 出错的那一行**整行停用**（永远不会被选中），其余照常；按程序设计准则 §4 第 9 条，数据错误不 `check` 崩溃。
- 无头跑一局即可看到全部体检结果，沿用 [程序设计准则 §10](../../../../MistRoost/程序设计准则.md#10-构建测试与ci门禁) 的无头命令。

## 9. 调试命令（开发构建）
