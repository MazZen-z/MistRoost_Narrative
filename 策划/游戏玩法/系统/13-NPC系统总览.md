## 2. 系统地图

```text
界面层（UI）      交互弹窗 / 对话框 / 爱心容器 / 交易面板 / 头顶气泡
                    ↑ 订阅事件、读数据                ↓ 发命令（选了哪项、送哪件、买卖多少）
逻辑层（玩法）    NPC 选项 → 对话会话 / 好感与送礼 / 商店与交易 / 头顶组件
                    ↓ 判断条件，如"季节＝春 且 心数 ≥ 3"               ↓ 发消息，如"主角卖了萝卜"
底层（Core）      条件内核：下拉选的条件＋且、或、非                消息管道 → NPC 记忆（谁听说了什么、几天后忘）

数据（表）        NPC 身份 / 对话结构＋字符串表 / 好感挡位 / 礼物喜好 / 商店·库存·价格规则 / 记忆规则 / 表情
状态（子系统）    好感、NPC 记忆、看过的台词、旗标、卖出统计、每个 NPC 的背包——按 NpcId / 容器名存；NPC Actor 只是投影
```

## 4. 贯穿全组的五条原则

1. **"满足某条件才……"都走同一套条件，"发生了什么"都走消息管道**。对话挑选、商店上架、打折、头顶标记、剧情解锁共用；新条件＝程序加一个条件结构体，编辑器下拉里自动出现，不改表结构；新事件＝发一种消息、记忆规则表加一行（[14 篇](14-条件与世界事实.md)）。
2. **结构进数据表，文字进字符串表**。编剧不碰结构、翻译不碰逻辑；文本键稳定，改措辞不换键（剧情编写准则 §5）。
3. **状态在子系统，不在 Actor**。NPC Actor 会随关卡流送销毁；好感、NPC 背包、看过的台词都存在子系统里，按 NpcId／容器名取（[程序设计准则 §2](../../../../MistRoost/程序设计准则.md#architecture)：Actor 是投影）。
4. **逻辑不认识界面**。NPC、对话、送礼、交易只发事件、收命令；界面订阅事件、推面板（[程序设计准则 §3](../../../../MistRoost/程序设计准则.md#domains)：任何下层都不依赖 UI）。
5. **数字全是占位，全部在表或项目设置里**。参考值注明来源，等你拍板；代码里不写死（程序设计准则 §4 第 2 条）。
