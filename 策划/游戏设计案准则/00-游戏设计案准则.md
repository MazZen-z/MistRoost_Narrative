# 游戏设计案准则

> 编号：DES-STD-001 · 版本：1.0 · 更新：2026-09-18
> 类型：策划生产规范 · Owner：主策／系统策划 · 会签：技术、UX、美术、叙事、QA、制作人
> 相关：项目总则 · [设计支柱](../游戏玩法/00-游戏总览.md) · [系统设计案模板](01-系统设计案模板.md)

## 1. 设计目的与准入

每份设计先回答“玩家获得什么体验、做什么决策、怎样知道成功”，再写按钮、数值与实现建议。围绕生活模拟、画符便利层、岚兽陪伴、中式静谧田园展开；不得因资源包里有武器、汽车或城堡便擅自扩玩法。

完整 3D 不改变已定核心循环与逻辑格子；表现升级不得悄悄改变工具范围、概率、田块规则或剧情事实。符咒原材料、岚日、亲密与技能等既有约束依各自规格，不在模板中另写一套。

规格必须区分：**已确认规则、候选方案、占位值、现有实现、验收证据**。类名示意、伪代码和参考游戏做法不自动成为程序已实现内容。

## 2. 设计层级与交付物

| 层级 | 应包含 | 不应包含 |
|---|---|---|
| 愿景／支柱 | 受众、体验承诺、差异、范围、非目标 | 未评估的全功能清单 |
| 核心循环 | 分钟／日／季节尺度的行动—资源—反馈—长期目标 | 只罗列系统名称 |
| 系统规格 | 状态、规则、数据、接口、异常、验收 | 模糊的“手感舒服”“随机给奖励” |
| 内容规格 | 作物、物品、角色、关卡、事件的结构与条目 | 重复实现同一规则 |
| 版本切片 | 最小可玩范围、依赖、DoD、排除项、回归矩阵 | 把最终大世界一次纳入 v0.1 |

## 3. 一份可施工设计案的最低内容

1. **元数据**：稳定需求 ID、版本、Owner、批准人、状态、目标里程碑、相关 ADR。
2. **玩家价值**：服务哪个支柱；玩家目标、反馈、取舍、失败与恢复；设计假设如何验证。
3. **范围与非目标**：本次做什么、不做什么，与已有系统的边界；用例参与者与触发位置。
4. **规则模型**：状态机、转移条件、优先级、时间与单位、概率入口、次数／冷却、边界与默认值。
5. **交互模型**：键鼠／手柄、输入上下文、焦点、取消、重映射、提示及可访问性。
6. **数据合同**：ID、字段名、类型、单位、约束、缺省、引用、持久化与本地化方式；示例是可校验的数据，不是宣传图。
7. **经济合同**：来源／消耗／储存上限、转化率、随机性、软锁风险、可重复刷取与防重复结算。
8. **3D 表现合同**：逻辑坐标与显示坐标、格子命中与可达性、动画与动作结果时机、交互距离、镜头／遮挡／提示；美术规格链接到权威文档。
9. **跨域接口**：事件／查询／命令的输入输出、拥有者、依赖版本、失败回退；叙事／音频／UI 需求逐项列出。
10. **存档与恢复**：需要持久化的最小状态、ID稳定性、跨日／跨场景、重复执行幂等、版本迁移；没实现的要写门禁。
11. **验证**：Given–When–Then 验收、边界和回归、可用性问题、性能场景、证据路径与通过者。
12. **风险与未决**：选项、影响、拍板角色、截止阶段；不可把待定项散在聊天里。

简单改动可使用精简模板，但不省掉 Owner、范围、规则变化、影响、验证和批准。

## 4. 规则、状态与数值的表达

- 状态机列出所有进入／退出条件及互斥、优先级；“下雨不需浇水”要说明判定时刻和跨日结算，不仅写一句口号。
- 数值用单位和边界：秒／游戏分钟、格／厘米、概率 `[0,1]` 或百分比必须注明；货币、数量、索引的有效范围明确。
- 所有概率通过统一运气入口；随机种子、重载行为和每次结算时刻明确，避免玩家读档获得无法解释的结果。
- 公式保留输入、输出和例子；引用数据表作为调参真源。描述“暂用”不代表可以在程序里硬编码。
- 表的 ID 与显示名称分开，改翻译或角色名不应改变存档身份；删除条目定义回退或迁移。
- 经济设计至少检查 0、1、上限、负值／溢出、背包满、跨日、重复触发和中断恢复。避免用无尽劳动抵消核心便利玩法的价值。

## 5. 交互与体验验收

原型应写“要回答的问题”，而不是只写“做个原型”。示例：玩家能否在不进入瞄准态时理解面前格动作？按住 LB／右键后能否理解角色停止、光标移动？不同高度是否选错田块？

- 玩法输入与菜单焦点分离；镜头缩放与快捷栏滚轮冲突必须列出上下文仲裁，不擅自更换已定键位。
- 吸附、目标高亮与碰撞反馈须与实际逻辑一致，不允许“看着能种但命中另一层”。
- 信息不只靠颜色；文本、图标、音频与动作至少有合理替代通道。
- 记录测试人群与设备、失败点、观察事实和改动，不用设计者主观手感替代可用性观察。
- 目标转化率、成功时间等测试阈值须先由负责人批准；没做测试不编百分比。

## 6. 跨专业交付

| 交给谁 | 策划应提供 | 接收方反馈 |
|---|---|---|
| 程序 | 状态／事件／数据字段、存档与错误语义、可测规则 | 可行性、接口、性能和迁移成本 |
| 美术／动画 | AssetID、屏幕用途、动作列表、接触点、可读性、状态差异 | 模型／骨架／动画合同、首件与资源预算 |
| 关卡 | 动线、可达性、互动密度、地形层级、空间预算 | 灰盒行程与镜头证据 |
| UI／音频 | 信息层级、状态与错误反馈、焦点／取消、文本键／提示事件 | 版式、动效、混音、可访问性与本地化 |
| 叙事 | 解锁条件、角色事实、变量／奖励、世界状态接口 | 剧情节点、文本键、触发冲突与正史影响 |
| QA | 正常／失败／边界用例、初始数据、种子、测试命令需求 | 缺陷、覆盖、回归与证据 |

不以“美术自由发挥”替代交互规格，也不把程序实现细节写死到每份设计案。程序架构只有一个入口：`MistRoost/程序设计准则.md`。

## 7. 审批与变更

`Draft（探索）→ Review（可评审）→ Approved（可制作）→ Implementing → Validated`。实现状态与文档批准状态分别记。规则改变先更新 ADR／影响评估，再更新数据、程序、美术、叙事、测试和文档；不能只修改一张表便认为全项目同步。

涉及概率、奖励、时间、输入、经济、存档、任务条件或镜头的改动必须列出受影响用例。版本冻结后按项目变更流程，不以“只是改几个数字”绕过回归。

## 8. 策划 DoR / DoD

**DoR**：问题和范围明确；核心规则可执行；依赖与未决有 Owner；验收不依赖审美猜测。

**DoD**：已按批准规则联调；边界／异常与相关回归通过；数据和文本键可校验；体验结论有记录；所有未解决事项有缺陷／例外编号；不将概念、代码写完或截图完成当成玩法完成。
